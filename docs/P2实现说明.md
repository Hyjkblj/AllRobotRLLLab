# P2 后端闭环实现说明

P2 将 P0/P1 的契约和应用服务接到一套可替换的后端基础设施边界。默认开发模式使用可恢复的 `Local File Mode`：不依赖 PostgreSQL、Redis 或 MinIO，元数据写入 `runtime/` 文件仓库，任务写入本地队列；显式设置 `ROBOTLAB_MODE=memory` 仍可用于纯内存单元测试。配置 `DATABASE_URL` 后使用 PostgreSQL UoW，配置 MinIO 参数后使用 MinIO 对象存储。

## 已实现能力

- 项目、成员和角色：`owner`、`editor`、`viewer`；写操作需要 editor，成员管理需要 owner；
- 资源和资源版本：对象 key 不使用用户路径，上传会话返回短期 PUT URL，complete 后进入 `VALIDATING`，worker 校验后才变为 `READY`；
- Run/Attempt：Run 幂等键、manifest freeze、Attempt 重试不覆盖历史、取消、状态机迁移、worker heartbeat；
- 事件：每个 attempt 的连续 `seq`，SSE 支持 `after_seq` 和 `Last-Event-ID` 恢复；
- 审计：项目创建、成员变更、资源创建/上传完成、Run 创建/取消/重试均产生审计事件；
- Outbox：数据库事务边界内登记事件，`OutboxDispatcher` 将其投递到 `asset-io`、`motion-cpu`、`isaac-gpu` 或 `maintenance` 队列；队列 envelope 具备幂等键；
- Artifact：worker 注册对象元数据，下载前做项目权限校验并返回短时 URL；
- PostgreSQL 16/Redis 7/MinIO Compose 和 SQL migration：`infra/compose/docker-compose.p2.yml`、`infra/migrations/001_p2_core.sql`。
- PostgreSQL/Redis/MinIO/Celery 客户端已锁定到平台 Conda 环境；`/api/v1/health/infrastructure` 在 Compose 依赖未配置或未连接时返回 `pending/degraded`，不会把本地文件或内存替身伪报为生产基础设施就绪。
- PostgreSQL UoW 已覆盖项目/成员、Run/Attempt、事件、审计、outbox、Asset/AssetVersion 和 Artifact；`users.external_id` 映射 API 外部身份，`run_idempotency` 持久化请求幂等键。迁移使用 `001_p2_core.sql`、`002_p3_artifacts.sql`、`003_external_identity_and_idempotency.sql`。

## P2 API

```text
POST/GET  /api/v1/projects
GET       /api/v1/projects/{id}
GET       /api/v1/projects/{id}/assets
GET       /api/v1/projects/{id}/runs
POST      /api/v1/projects/{id}/members
POST      /api/v1/projects/{id}/assets
GET       /api/v1/assets/{id}/versions
POST      /api/v1/assets/{version_id}/upload-complete
POST      /api/v1/assets/{version_id}/upload-url
PUT       /api/v1/uploads/{object_key}          # Local File Mode browser upload
GET       /api/v1/objects/{object_key}          # Local File Mode browser download
POST      /api/v1/assets/{version_id}/validate   # X-Worker-Id only
POST      /api/v1/runs
GET       /api/v1/runs/{id}
GET       /api/v1/runs/{id}/events
POST      /api/v1/runs/{id}/cancel
POST      /api/v1/runs/{id}/retry
POST      /api/v1/runs/{id}/status               # X-Worker-Id only
POST      /api/v1/runs/{id}/heartbeat             # X-Worker-Id only
POST      /api/v1/runs/{id}/events                # X-Worker-Id only
POST      /api/v1/artifacts                       # X-Worker-Id only
GET       /api/v1/artifacts/{id}
GET       /api/v1/health/infrastructure
```

请求身份使用开发环境的 `X-User-Id`，默认 `local-user`；生产部署应由 OIDC/反向代理注入稳定身份。worker 写接口要求 `X-Worker-Id`，生产环境再由短期 job token 中间件替换该开发标记。

## 本地运行

```powershell
conda activate allrobotrl-platform
python -m pytest -q
docker compose -f infra/compose/docker-compose.p2.yml up -d
uvicorn apps.api.main:app --reload
```

无数据库本地模式：

```powershell
$env:ROBOTLAB_MODE = "local_file"
$env:ROBOTLAB_RUNTIME_DIR = "$pwd/runtime"
python -m tools.robotlab init --mode local_file
python -m tools.robotlab start --mode local_file --port 8000
```

`LocalFileUnitOfWork` 使用进程锁、每个 Run 独立的 `runs/<run_id>/state.json`、`manifest.json`、`events.jsonl`、`metrics.jsonl` 和可重建 `index.json`；`LocalFileTaskDispatcher` 使用原子替换的本地任务队列并保留幂等键，`backend.app.workers.local_worker` 在本机消费该队列。机器重启后 API/worker 重新加载这些文件，不依赖进程内存。配置数据库后由 PostgreSQL 连接事务提供真实提交/回滚，API/application/domain 契约在两种模式间保持不变。

PostgreSQL 模式启动前执行：

```powershell
conda run -n allrobotrl-platform python -c "import os; from pathlib import Path; from backend.app.infrastructure.postgres import PostgresDatabase; PostgresDatabase(os.environ['DATABASE_URL']).apply_migrations(Path('infra/migrations'))"
```

SSE 支持 `after_seq`、`Last-Event-ID` 和可选 `attempt_id`；重试不会覆盖旧 attempt 的日志。
