# 多机器人架构实施状态

本轮将平台核心与 G1 执行实现拆分为注册表和 provider 边界。默认部署仍注册 `unitree_g1_29dof`，但 adapter、任务和运行时均通过 composition root 装配；新增机器人可以通过 `ROBOT_ADAPTER_MODULES` 加载，不需要修改项目、资源、Run 或产物协议。

## 已完成

- `RobotAdapterRegistry`：按 `robot_id` 解析 RobotSpec、资产自检和动作编译 adapter。
- `PlatformAssembly`：API、Local worker、Celery worker 共用同一套 adapter/task/provider 装配。
- `TaskRegistry`：按 `task_id` 声明目标机器人、场景、训练 provider 和 sim2sim adapter。
- `TrainingProviderRegistry` / `Sim2SimRegistry`：按稳定名称选择外部执行实现，fake smoke 不会误选已安装的第三方 provider。
- `UnitreeRLLabProvider`：G1 的可选外部 provider，封装 Unitree RL Lab 的 train/play/export 入口。
- `NativeIsaacLabProvider`：平台侧原生 Isaac task 的进程契约；只接受显式 `NATIVE_ISAAC_*_COMMAND`，不会回退到 Unitree RL Lab。
- `apps.isaac_tasks.entrypoint`：平台拥有的 train/play/export 稳定入口和任务注册协议。
- `TrainingService`：根据 Run Manifest 的 `robot_id` 解析适配器，根据选定 backend 解析训练 provider 和 sim2sim adapter。
- 动作 detector、GMR normalizer、MotionPipeline 和策略包元数据支持由目标 RobotSpec 提供 DoF、控制周期、场景和算法参数。
- API 提供 `/robots`、`/tasks`、`/training-config/schema`；前端从这些 API 读取机器人与任务，并在动作、训练页面选择目标机器人。
- Reward catalog 已支持通配的通用 shaping terms，并通过 `robot_id`/`task_id` scope 过滤、校验和创建版本。
- `fixture_biped_2dof` 作为仅测试 adapter 验证了 2 DoF RobotSpec、任务派生、动作编辑和训练服务选择逻辑。
- `apps.isaac_tasks.entrypoint` 支持通过 `ISAAC_TASK_MODULES` 加载 Isaac 环境中的任务注册模块。
- `collect_runtime_manifest.py` 保留 G1 兼容资产字段，并新增 `robot_assets`，按 `ROBOT_ADAPTER_MODULES` 采集每个 RobotSpec 的模型/URDF 内容 hash。
- MuJoCo 旧原型的 G1 默认模型仅在未指定机器人身份时生效；显式选择其他机器人但未提供模型或 RobotSpec 资产时会直接失败，避免跨机器人模型串用。
- 动作流水线在未提供 `MotionEditConfig` 时使用 `RobotAdapterRegistry.default_robot_id`，不会被兼容构造参数中的旧 adapter 覆盖；验收页和编辑器导出文件名均按当前 Run/RobotSpec 动态显示。
- 未带机器人 scope 的 `MotionSourceRegistry` 与 `default_reward_config()` 现在输出通用契约（不再默认为 G1）；旧 G1 集成必须显式传入 `unitree_g1_29dof`/`g1_mimic`，动作 detector 另提供 `legacy_g1()` 兼容工厂。
- staging/production API 启动检查会对装配后的每个 RobotAdapter 执行 `self_check()`；部署配置不再在通用 Settings 层硬编码 `G1_MJCF_PATH`，缺失的是哪个机器人资产会明确报告哪个 `robot_id`。

## 尚未完成

- G1 仍是默认 adapter；`unitree_h1_19dof` 生产级 RobotSpec adapter 已加入，使用公开 MuJoCo Menagerie H1 资产并通过 `H1_MJCF_PATH` 或 `MUJOCO_MENAGERIE_PATH` 配置。默认部署不自动加载 H1，需在 `ROBOT_ADAPTER_MODULES` 中显式启用。
- G1 的真实 Isaac task 仍需在目标 Isaac Lab 环境中注册到 `apps.isaac_tasks`，并配置 `NATIVE_ISAAC_TRAIN_COMMAND`、`NATIVE_ISAAC_EXPORT_COMMAND`。
- Reward term 的实现仍是通用 mimic shaping 集合；不同机器人需要继续补充其接触、执行器和验收专用 term。
- G1 使用 Unitree MuJoCo runner；H1 使用通用 command-backed MuJoCo runner（`H1_SIM2SIM_COMMAND`），不假设 DDS、sensor 顺序或 Unitree 控制器。第二个机器人仍需在目标环境提供真实控制命令和验收阈值。
- API 与 worker 已在 train/export/sim2sim 边界按 Run 的 `robot_id + task_id` 检查 provider/adapter 支持；错误的 G1/H1 组合会在入队前和消费时 fail-closed。

## 验收边界

开发或契约测试可以使用 `fake_smoke`。staging/production 必须选择真实 provider；Native Isaac provider 未配置命令时会明确失败，不能把 smoke 结果标记为真实训练或 sim2sim 通过。未传 RobotRegistry 的任务目录现在为空；旧 G1 调用必须显式使用 `legacy_g1_task_registry()`。
