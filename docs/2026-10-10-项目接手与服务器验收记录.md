## 1. 当前结论

当前已经用服务器真实运行证据证明 G1 的以下技术链路能够执行：

```text
合规 TrainMotionNPZ
  -> 项目自有 Isaac Lab DirectRLEnv / RSL-RL 训练
  -> 二进制 checkpoint
  -> TorchScript + ONNX 导出
  -> 项目自有 Unitree G1 MuJoCo evaluator
  -> 三个固定 seed 的闭环仿真
  -> 指标与正式质量门报告
```

这次使用的是仅 2 iterations 的短训练。训练、导出和三个 MuJoCo 进程均真实完成，但策略质量报告为 `FAILED`，因此没有也不应进入 `READY_TO_DOWNLOAD`。

目前仍不能宣称完整产品业务链路已经端到端跑通。尚缺从前端/API 创建项目和 Run 开始，经对象存储、异步 worker、真实 GVHMR/GMR、动作编译、正式训练、导出、三 seed 通过，最终在前端下载策略包的一次完整运行证据。

## 2. 不可违背的架构决策

1. Unitree RL Lab 只可作为设计和配置参考，不是平台运行时依赖。
2. G1 训练由本项目的 `apps/isaac_tasks` 实现，不调用 Unitree RL Lab 的 train/play/export 脚本。
3. 外部 GMR、GVHMR、Isaac Lab/Isaac Sim 和 Unitree MuJoCo 使用独立环境。平台通过进程参数、文件、JSON manifest 和 SHA-256 编排，不能在平台进程中直接混合导入全部第三方依赖。
4. `RobotAdapterRegistry`、`TaskRegistry`、`TrainingProviderRegistry`、`Sim2SimRegistry` 是多机器人扩展边界。通用业务层不得重新写死 G1 的 29 DoF、`g1_flat` 或 `0.02`。
5. 生产路径必须 fail closed。不能用 fake smoke、空 MuJoCo 场景或 runtime doctor 结果冒充真实训练和 sim2sim。
6. 不得为让 2-iteration 策略通过而降低正式阈值。
7. 服务器每次使用 conda 前先执行：

```bash
source /ai/python/miniconda3/etc/profile.d/conda.sh
```

### 4.4 项目自有 G1 MuJoCo evaluator

关键文件：

- `apps/mujoco_sim2sim/g1.py`
- `backend/app/runtime/unitree_sim2sim_runner.py`
- `backend/app/application/training_service.py`

能力：

- 加载官方 Unitree MuJoCo `unitree_robots/g1/scene_29dof.xml`。
- 支持 ONNX Runtime，另支持 TorchScript。
- 重现 376 维原生训练 observation。
- 使用参考动作加 policy action 形成关节目标。
- 使用与 G1 Isaac 配置对齐的 PD gains 生成 torque，并遵守 actuator torque limits。
- 物理步长 `0.002s`，每个 `0.02s` policy step 执行 10 个 MuJoCo substeps。
- 每个 seed 写出 `metrics.json`、`trace.csv`、`seed_report.json`，可选最终帧 PNG。
- `TrainingService.sim2sim` 会重新 materialize 冻结动作、校验 manifest SHA，并优先选择 ONNX 产物。
- runner 有项目默认 evaluator，不再强制 `UNITREE_SIM2SIM_COMMAND`；该环境变量仍可作为显式覆盖。

正式指标：

- `survival_rate`
- `joint_rmse_rad`
- `root_position_rmse_m`
- `orientation_error_deg`
- `saturation_ratio`
- `foot_slip_mps`

Isaac/URDF 有 `left_rubber_hand` 和 `right_rubber_hand`，官方 Unitree MuJoCo XML 没有这两个 body。evaluator 不伪造映射；MuJoCo 指标只要求实际存在且确实使用的 pelvis 和双脚 body。

### 8.2 SSH 断开事件

之前三 seed 命令使用了：

```bash
python ... || exit 1
```

第一次 evaluator 因错误格式常量失败后，`exit 1` 退出了登录 shell，看起来像服务器断开。服务器本身没有崩溃。后续交互式 SSH 命令应保存 `$?`，不要直接 `exit`。

### 8.3 ONNX Runtime 警告

服务器会输出关于 `virtio0` PCI bus id 的 ONNX Runtime warning。导入和推理均成功，该 warning 不是失败原因。

### 8.4 seed status 的含义

手工聚合报告中每个 `SeedEvaluation.status=PASSED` 表示 evaluator 进程 `exit_code=0`。最终 `Sim2SimReport.status=FAILED` 表示指标没有通过质量门。不要把 seed 进程状态当成策略验收状态。

后续可以考虑让 runner 根据 `seed_report.failure` 把 seed status 标成 `FAILED`，但必须同步检查现有 API/UI 对 status 的语义，避免破坏“进程结果”和“质量结果”的分层。

### 8.5 sim2sim 指标仍需长期校准

当前 evaluator 是真实闭环，不是假数据，但正式生产前仍需用多类经过充分训练的策略校准：

- 足滑使用双脚 body 高度和水平速度启发式。
- root error 对世界坐标参考动作计算。
- Isaac URDF 与 Unitree MuJoCo XML 的接触、惯量和 actuator 差异会影响阈值。
- 当前 seed 随机化包含初始关节/根位置扰动和摩擦扰动。

校准必须基于合格策略和多动作样本，不得用当前 2-iteration 策略反向放宽阈值。

## 10. 推荐的下一步顺序

### P0：用正式 Run 打通平台自动编排

不要立即做长时间训练。先使用当前合规 TrainMotionNPZ 和短训练配置，从 API 创建真实 Run，让 Local File Mode 或 Compose worker 自动完成：

```text
API Run
  -> frozen manifest
  -> train worker
  -> export worker
  -> sim2sim worker
  -> FAILED quality report
```

这一步预期仍因 2 iterations 得到 `FAILED`，但必须证明状态机、队列、对象存储和 artifact 注册无需手工拼接。

### P0：修复自动链路暴露的问题

重点核对：

- `SIM2SIM_PYTHON` 是否指向 `allrobotrl-mujoco/bin/python`。
- runtime registration 是否记录 Unitree MuJoCo path 和 interpreter。
- API、worker 是否共享同一个 `ROBOTLAB_RUNTIME_DIR`。
- export files 是否由 `TrainingService._policy_path` 优先选中 ONNX。
- sim2sim 是否收到 frozen TrainMotionNPZ，而不是服务器任意路径。
- report、trace、seed report 和最终 bundle 是否全部注册到对象存储。

### P1：正式 GPU 训练并复验

在自动短链路成立后，提高 iterations/num_envs，保留相同 motion、manifest、导出和阈值。训练时间和资源参数必须记录到 Run Manifest。正式训练结束后重新执行三个固定 seed，不覆盖本次短训练证据目录。

### P1：真实视频动作链路

选择可控短视频，完成 GVHMR -> GMR -> MuJoCo compiler -> TrainMotionNPZ。保存每一阶段输入输出 SHA、runtime revision、日志和 manifest。

### P2：前端验收

用 Playwright 覆盖导入、动作处理、训练监控、sim2sim 报告和下载主流程；不能只验证 Vite build。

### P2：第二机器人

建议在 G1 自动闭环稳定后选 H1。必须补真实 Isaac task、模型资产身份、动作映射、export 和独立 MuJoCo evaluator/阈值，而不是复用 G1 的 29 DoF 假实现。
